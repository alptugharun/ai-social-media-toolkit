# Paid implementation and commercial support

The public repository is the proof layer. Paid work is for creators, agencies, brands and teams that want to **skip setup, customization and operational maintenance** without turning the open-source project into a paywall.

## What stays public

Existing open-source and Creative Commons material keeps the license stated in this repository. Commercial services do not retroactively remove those rights.

## Start with one concrete outcome

The default commercial engagement is an **implementation sprint**, not a vague “AI consulting” package.

You bring one real job. The paid work can include:

1. **workflow diagnosis** — map the current process, bottleneck, required inputs and systems;
2. **architecture choice** — decide whether the job actually needs a prompt, assistant, Agent Skill, MCP/API integration or automation;
3. **working implementation** — configure the smallest useful system for the agreed scope;
4. **trust boundaries** — document permissions, secrets, external calls, writes and approval points;
5. **failure paths** — show what breaks, how to detect it and how to recover;
6. **handoff** — provide a usable runbook so the workflow is not dependent on one chat session.

The exact deliverable depends on the job. A successful engagement should end with something the client can **run, review and maintain**, not only a slide deck.

## Current paid-service lanes

These are service offers, not a claim that a hosted SaaS or subscription product already exists.

### 1. AI workflow implementation

**Good fit:** a repetitive knowledge/creator/operations task already exists, but the current AI process is manual, inconsistent or difficult to hand off.

Possible deliverables:

- prompt / assistant / Agent Skill / MCP / automation architecture;
- installation and configuration;
- provider-portable instructions where practical;
- approval and recovery paths;
- onboarding and operating documentation.

### 2. Creator operations systems

**Good fit:** a creator, agency or brand needs a repeatable path from research to production and QA.

Possible deliverables:

- content research and prioritization workflow;
- Canva / Pinterest / Reels production system;
- creator analytics and repeatable reporting;
- reusable briefs, templates and QA gates;
- human-reviewed publishing flow.

### 3. Custom radar / intelligence workflow

**Good fit:** the same research question must be answered repeatedly with traceable evidence.

Possible deliverables:

- a narrow recurring monitoring question;
- permitted public, first-party or client-owned evidence inputs;
- prioritization/scoring rules;
- repeatable report format;
- review gates and escalation rules;
- evidence and uncertainty notes.

### 4. Audit and hardening

**Good fit:** a workflow already exists but its permissions, reliability, onboarding or documentation are unclear.

Possible deliverables:

- AI workflow/tool-stack review;
- Agent Skill and MCP permission review;
- failure-path and onboarding audit;
- repository trust/documentation review;
- prioritized remediation plan and focused fixes where agreed.

## Good fit / poor fit

A project is a **good fit** when:

- there is a real recurring job rather than “we should use AI somehow”;
- the owner can explain the current workflow and pain point;
- success can be observed;
- required data and integrations can be used lawfully and with permission;
- a human owner remains responsible for consequential publishing or account actions.

It is a **poor fit** when the request depends on fake engagement, bypassing platform controls, fabricated evidence, unrestricted scraping, hidden surveillance, guaranteed virality/revenue or unsupported access to private systems.

## What to send for a useful first conversation

Do not send credentials or confidential data. Start with four answers:

1. **What job must be completed?**
2. **How do you do it today?**
3. **Where does time, quality or reliability break down?**
4. **Which systems must or must not be connected?**

## Not sold as evidence

A GitHub clone, star, automated report or local test is **not** presented as a paying customer, independent adoption, revenue or production success.

Public issue votes are prioritization signals, not commercial commitments.

## Future paid products

Hosted dashboards, recurring reports, premium support or subscription software should only be introduced after repeated real-user demand is demonstrated.

The intended ladder is:

**open proof → implementation service → repeatable productized service → recurring workspace/reporting → hosted product only when demand justifies it**

Pricing, contracts, payment details and commercial commitments are handled separately from open-source issue voting.
