# Focus & Traction Playbook

Research snapshot: **2026-09-27**

This playbook exists because the project now has enough breadth that the next risk is not lack of ideas. The next risk is **scope expansion without adoption proof**.

## Strategic conclusion

The strongest differentiation is not that every individual feature is globally unique.

The stronger position is the combination of:

**social-media domain knowledge + AI Agent Skills + evidence-aware research + automation + commercial workflow design**

The repository should therefore optimize for **proof, reuse and distribution**, not raw feature count.

## Primary wedge

The repository's core identity is:

**Open-source creator operations for AI-assisted social media and digital visibility.**

Pinterest, Maps/local intelligence, Reels, influencer workflows and commercial research are supporting lanes inside that creator-operations system.

They should not automatically become separate products unless evidence shows that a specific lane deserves its own product.

## Commercial ladder

The default commercial sequence is:

1. public proof / open-source core
2. implementation and customization service
3. productized recurring service
4. paid recurring intelligence/reporting
5. hosted workspace / SaaS
6. marketplace / sponsor / enterprise layers after adoption evidence

GitHub is primarily:

- proof
- distribution
- inspectable open core
- installation surface
- trust / authority

It is not assumed to be the primary revenue source.

## Expansion Gate

Before adding a new Agent Skill, automation or product lane, answer:

1. Does an existing skill already cover at least 70% of the job?
2. Can the idea improve an existing workflow instead of creating a new one?
3. Is there external evidence of demand, reuse or a clearly identified buyer?
4. Can the first proof be measured?
5. Does the new lane strengthen the creator-operations positioning?
6. What will be removed, merged or deprioritized if this is added?

If the answer to 1 or 2 is yes, prefer improving the existing asset.

If the answer to 3 or 4 is weak, keep the idea in research mode instead of expanding the product surface.

## Traction evidence hierarchy

Prefer real evidence in this order:

1. repeated real-world use
2. paid client / buyer validation
3. external installs / reuse
4. external contributors / PRs / issues
5. stars / forks / watchers
6. referral traffic / demo usage
7. qualitative feedback
8. internal activity

Important:

**Commits prove activity, not adoption.**

**Skill count proves scope, not product-market fit.**

**Stars are a weak interest signal, not revenue.**

## Proof metrics

Track when available:

- stars
- forks
- subscribers/watchers
- external contributors
- external issues / discussions
- releases
- install or package usage where measurable
- repeat usage
- referral traffic
- client adoption
- paid pilots
- case studies
- retention
- revenue / MRR only when genuinely measured

Never invent missing metrics.

## Focus status

The traction report should use three plain-language states:

### BUILD PROOF

Use when the project is still mostly internally driven.

Action:

- improve onboarding
- strengthen examples
- ship working demos
- reduce friction
- create evidence-backed case studies
- distribute to qualified audiences
- avoid broad new product lanes

### VALIDATE WEDGE

Use when external reuse or buyer interest appears.

Action:

- identify which workflow creates repeated value
- run a narrow real-user test
- measure repeat use
- test a small paid offer

### SCALE WHAT WORKS

Use only after repeated use or commercial validation is visible.

Action:

- package the strongest lane
- automate delivery
- add hosted convenience
- consider Marketplace / Sponsors / SaaS

These states are operating guidance, not industry-standard benchmarks.

## Current operating principle

For this repository, the next question is no longer:

**"What else can we add?"**

It is:

**"Which existing workflow earns the strongest external proof?"**

## Distribution priorities

Before building more breadth, prioritize:

- better quick starts
- working examples
- concrete before/after demonstrations
- one-command installs
- clear use cases
- Behance / LinkedIn / website case studies
- legitimate community distribution
- real user feedback
- measured reuse

## Core principle

**Breadth creates possibilities. Traction decides where depth belongs.**
