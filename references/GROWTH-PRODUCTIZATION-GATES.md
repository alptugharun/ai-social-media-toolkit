# Growth & Productization Gates

Research snapshot: **2026-09-29**

This document defines how the project should move from public proof to paid companion products without confusing activity, stars or internal enthusiasm with demand.

## Core rule

**Do not paywall useful public value just because the repository gets attention.**

A paid layer should remove meaningful operational friction through implementation, connected systems, maintained automation, account-specific configuration, reporting, support or managed delivery.

## Evidence hierarchy

Strongest evidence first:

1. paid pilot or explicit buyer commitment
2. repeated use by independent external users
3. direct requests for a deeper / managed / team version
4. external installs, forks, issues or contributions
5. qualified referral traffic and demo usage
6. stars / watchers
7. internal activity

Stars are a discovery signal, not a pricing signal.

## Operating states

### BUILD PROOF

Use when the project is mainly internally driven.

Actions:

- improve onboarding
- ship examples and starter materials
- reduce installation friction
- ask for real workflow feedback
- publish release-ready proof
- improve distribution

Do **not** create a paid wall.

### VALIDATE PAID LAYER

Enter this state when at least one strong buyer signal exists, such as:

- a paid implementation request;
- repeated use plus a direct request for more convenience/support;
- multiple independent users asking for the same deeper workflow;
- clear client demand for setup, reporting or recurring delivery.

Actions:

- define one narrow paid outcome
- keep the open core useful
- prepare a small pilot
- record delivery cost and repeatability
- test willingness to pay with a real buyer

### PRODUCTIZE

Use only after the same outcome is delivered successfully more than once or repeated buyer demand is visible.

Possible paid layers:

- implementation / customization
- productized recurring service
- maintained automation pack
- editable workspace
- team/client operating system
- recurring intelligence/reporting
- hosted convenience layer

### SCALE

Use only after repeat use, retention or repeat purchase justifies automation and infrastructure.

Possible next steps:

- hosted product
- billing
- team permissions
- Marketplace
- Sponsors / partner model
- managed integrations

## Current candidate paid companions

These remain hypotheses until evidence promotes them:

- Creator Prompt OS
- Pinterest Growth OS
- Reels Production OS
- Canva + AI Content Factory
- Creator Automation Vault
- AI Creator OS
- implementation and customization services

## Automated research boundary

Automated systems may:

- monitor demand and competitor signals
- compare repository growth surfaces
- identify repeated feature requests
- draft pricing hypotheses
- prepare product briefs
- prepare branches / pull requests for low-risk public improvements
- flag when the evidence state changes

Automated systems must **not** autonomously:

- activate checkout or billing
- change live prices
- accept contracts
- buy ads
- promise revenue
- remove useful free functionality to manufacture scarcity

Those actions require an explicit commercial decision.

## Stop conditions

Pause or merge a product lane when:

- external use remains absent after repeated distribution tests;
- a stronger existing workflow already solves the job;
- the buyer is unclear;
- support cost exceeds likely value;
- the feature depends on restricted scraping or unstable platform behavior;
- interest is driven only by internal activity or vanity metrics.

## Current direction

The project's default path remains:

**open-source proof → external use → implementation service → productized recurring service → paid intelligence / managed automation → hosted product when justified**
