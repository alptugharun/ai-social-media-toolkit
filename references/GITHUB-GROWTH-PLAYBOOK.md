# GitHub Growth & Discovery Playbook

Research snapshot: **2026-09-24**

This playbook is for evidence-aware repository growth. It is not a promise of virality.

## What GitHub Actually Rewards

GitHub uses **stars**, not likes, as one of its strongest visible popularity signals. GitHub states that many repository rankings depend on stars, and Explore surfaces popular repositories based on stars.

Discovery also happens through:

- Trending
- Explore
- Search
- Topics
- Profiles and pinned repositories
- Social sharing and external references
- Community activity

Official references:

- https://docs.github.com/en/get-started/exploring-projects-on-github/saving-repositories-with-stars
- https://docs.github.com/en/get-started/exploring-projects-on-github/discovering-projects-on-github
- https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes

## Current Market Signal

The current GitHub Trending page is heavily represented by:

- agent runtimes
- reusable Agent Skills
- MCP / agent tooling
- agent-native interfaces
- local or self-hosted AI
- developer productivity systems
- tools with measurable performance claims

Treat a single day of Trending as a **fresh signal**, not a permanent market truth.

## Patterns Seen in High-Star Repositories

### 1. One-line outcome

A visitor should understand the outcome in seconds.

Weak:

> AI tools and resources.

Stronger:

> Turn creator research signals into installable social-media Agent Skills.

### 2. Fast first success

High-adoption repositories commonly reduce time-to-value with:

- one install command
- a 30-second quick start
- one obvious first command
- copy-paste examples
- sensible defaults

### 3. Proof, not adjectives

Prefer:

- benchmark
- before / after
- test count
- supported platforms
- measured speed
- case study
- real usage example

over vague claims such as "ultimate", "revolutionary" or "viral".

### 4. Cross-tool portability

Agent Skills currently have strong distribution potential because the format is reusable across multiple agent hosts.

When practical, make the same skill usable from GitHub Copilot, Claude Code, Cursor, Codex, Gemini CLI and other compatible runtimes.

### 5. Trust signals

Useful trust signals include:

- clear license
- tests
- CI
- security notes
- source transparency
- no hidden API requirements
- explicit data / privacy behavior

### 6. A narrow wedge with broader expansion

A repository often earns attention by solving one painful job extremely well first, then expanding.

Do not launch many shallow skills merely to increase file count.

### 7. Memorable packaging

The best project names and descriptions tend to communicate:

**who it is for + what it does + why it is different**

The README should answer:

1. What is this?
2. Why should I care?
3. How do I try it now?
4. What proof exists?
5. What can I do next?

## Search Demand: Important Limitation

GitHub does **not** expose a public exact "monthly search volume" metric for repository searches.

Therefore the toolkit must never report invented GitHub search volume.

Use proxies instead:

- current Trending presence
- recent star velocity
- recent high-star repositories
- repository search result count
- topic frequency
- forks
- active maintenance
- issue / discussion demand when available
- external search or trend data when available

Label each metric correctly.

## Opportunity Model

Use four dimensions: demand, supply, proof potential and distribution fit.

A large repository search result count does not prove a market is saturated. It is only a supply proxy.

Prefer concepts that can demonstrate value with a before/after, ranked output, saved time, fewer manual steps, a reproducible audit or another measurable result.

## Skill Gap Method

Do **not** ask:

> What has nobody ever built?

That is almost impossible to prove globally.

Ask instead:

> Which useful job has strong adjacent demand, weak direct competition, and a result we can prove?

For every candidate:

1. Define the job-to-be-done.
2. Search GitHub for direct and adjacent solutions.
3. Record repository-result count.
4. Inspect the strongest competing implementations.
5. Identify the missing workflow or user type.
6. Design a narrower, more useful contract.
7. Build a small example.
8. Add tests or measurable acceptance criteria.
9. Publish only after a human review.

## High-Potential Skill Directions

These are hypotheses to test, not claims of uniqueness.

- **brand-voice-regression-test** — detect voice drift across a batch of content
- **content-decay-refresh** — find aging evergreen assets and produce evidence-backed refresh plans
- **proof-to-case-study** — convert evidence and metrics into claim-safe portfolio case studies
- **cross-platform-cannibalization-auditor** — find duplicate / competing content across channels
- **sponsor-readiness-auditor** — audit creator assets, proof and positioning before brand outreach
- **visual-trend-translator** — convert a visual trend into original brand-safe executions
- **hook-experiment-designer** — turn one idea into testable hook hypotheses with KPI contracts
- **local-business-demand-to-content** — turn reviews, FAQs and local demand signals into content opportunities
- **agent-skill-gap-miner** — identify high-demand / low-direct-supply Agent Skill opportunities

The automated radar should re-score these ideas instead of assuming they remain attractive.

## Growth Loop

**Observe → Measure → Find gap → Build one useful asset → Prove it → Package it → Distribute it → Measure adoption → Improve**

Track stars, forks, installs when measurable, external mentions, website referrals and commercial inquiries.

## Monetization Paths

Popularity is not revenue by itself.

Possible paths after real usage appears:

- GitHub Sponsors
- commercial support
- consulting / implementation
- premium templates or training
- agency leads
- sponsored educational content
- paid integrations
- workshops

Do not add monetization friction before the free repository delivers obvious value.

## Rule

**Optimize for usefulness first. Distribution amplifies usefulness; it cannot replace it.**
